### Puppeteer capabilities

- **`POST /api/launch_recipe` (P1)** — ad-hoc recipe launch through
  the puppeteer's queue_run_ite. Accepts `{pipe}` (single) or
  `{pipes: [...]}` (multi-pipe queue). Writes a control_override
  with `pipeline: run_queue` and one entry per pipe, clears
  step-queue_run_ite state, spawns pipeline_runner in the puppeteer
  CWD detached. Refuses if another runner is alive (409, override
  with `force: true`).
- **`POST /api/sync_overrides` + `~/bin/sync-overrides.sh`** —
  bidirectional sync of `pipes/*/override/` AND `pipes/*/data/`
  between laptop and mini. Symlinks skipped (--no-links). Three
  access surfaces: CLI, puppeteer step (`sync_overrides_ite.coffee`),
  HTTP endpoint. Helper action executor has a `when 'sync_overrides'`
  branch pre-wired so the helper corpus can grow this action later.
- **`GET /api/sat_matrix`** — SSH-scrapes each hf__qwen__* pipe's
  out/*.yaml verdicts, aggregates into a per-pipe row with all 4
  configs × 2 sides + elementary + story. Includes a derived
  `best.diary` (max-cell across 8 diary variants, ties broken toward
  simpler-config + adapter-on) and a human-readable
  `recommendation` line.
- **`GET /api/sat_text?pipe=X&file=Y`** — SSH-cats a single
  pipe/out/ file, returns text/plain. Restricted to
  `out/*.txt|.yaml|.json` for safety.
- **SAT Grades panel** on puppeteer UI (port 4311) — cross-pipe
  grid with per-cell click-to-see-raw-text, a "best diary" column
  showing the winning (config/side) tag, and an italic
  recommendation line per pipe row. Auto-refreshes every 30s.

## Findings (0.6B — the only pipe with completed extended-ladder data at EOD)

Diary ablation matrix, hard_pass_count / hard_total:

    | config    | adapted | base |
    | baseline  | 5/6     | 4/6  |  ← adapter helps
    | kag       | 4/6     | 5/6  |
    | chunks    | 4/6     | 5/6  |
    | both      | 5/6     | 6/6  |  ← BEST (recommendation)

Two hard findings from this pipe:

1. **Adapter helps ONLY at baseline (no context).** Once KAG or
   chunks are added, the raw model beats the adapter — the 0.6B
   rank-8 LoRA's capacity is exhausted competing with prompt
   context, and generation collapses into repetition (the "She
   had just moved to Portland, and the [emotion] of the locket
   haunted her" loop we saw in kag/adapted).
2. **The pipe's true ceiling is 6/6 at config=both, side=base**
   (no LoRA, both KAG + chunks). The recommendation the panel now
   surfaces: *"diary: 6/6 — run WITHOUT adapter (LoRA hurts here) ·
   with KAG + chunks context"*.

Framework gap: no current check catches "same clause repeated 5
times in a paragraph" — the repetition collapse in kag/adapted
scored 4/6 on the mechanical checks. Worth a new check.

## For tomorrow — new build: episodic story machine

Human's directive at EOD: *"we will look at the results and start
building a new episodic story machine. It uses all of our spine
generation stuff, and should need only small adaptation to our
story recipe, but with very different scenario and action."*

What that likely means:

- **Reuses the spine framework** — `sat_fixed_spine.yaml`'s shape
  (allowed_names + invariants + past_scraps + premise + emotional_arc)
  is the base contract. An episode is a story-instance keyed on
  a spine.
- **Small adaptation of the story recipe** — `writer/config/story.yaml`
  already exists as a story recipe. Adaptation likely means
  extending it (or forking to `episode.yaml`) to accept an
  "episode context" — prior episodes' facts, character continuity,
  serial-story constraints.
- **Different scenario and action** — the current diary/story SAT
  targets a single locked situation (Ari + locket). The episodic
  machine iterates: episode N reads what happened in episodes 0..N-1,
  keeps character/setting continuity, but drives new scenarios and
  actions in each episode.

Design questions worth asking the human tomorrow before building:

1. Is an "episode" the same 5-segment structure as a diary
   (scene/arrival/disturbance/reflection/realization) or a longer
   arc?
2. Is character continuity per-series (persistent Ari, Mira across
   all episodes) or per-episode (fresh cast per invocation)?
3. Where do the "scenario and action" for each episode come from
   — a human-authored season plan? Random draws from a scenario
   library? A generator step that proposes each episode's
   scenario given prior episodes?
4. Does the SAT ladder extend to episode-level grading (episode
   coherence with prior episodes, character consistency across
   time), or does per-episode grading fall back to the current
   diary/story graders?

## The real blocker — @frost-beta/mlx cross-step fragility

Same model, no adapter change, back-to-back `session_api.generate`
calls in ONE process. First one works, second one crashes inside
`mx.core.tidy`. This is the SAME class of failure the
`helper_ab_probe` had to work around with subprocess-per-probe
isolation (see the prior session summary — "native state in
@frost-beta/mlx persists across require-cache busts").

Fix options for tomorrow (pick one before touching sat_ladder.yaml
again):

1. **Consolidate the two diary sides into ONE step.** oracle_ask_sqlite
   does many generates per invocation and doesn't crash — the
   fragility is BETWEEN pipeline_runner steps, not within a step. A
   single `sat_diary_ite` that internally does both `adapted` and
   `base` generations and emits both artifacts sidesteps the issue.
   Simplest, closest to working.

2. **Subprocess-isolate each generate step.** Wrap `sat_diary_ite`
   and `sat_story_ite` to `spawnSync` a child process per call, à la
   helper_ab_probe. More work; more general fix; would also let
   Tier 1 + Tiers 2/3 truly parallelize in the future.

3. **Force a session teardown between steps.** Check whether
   `session_api` exposes a dispose hook the runner can invoke
   between steps that share a modelDir. If so, wire it into the
   step boundary.

Recommendation: (1) for the sweep this week (fastest), then (2)
as the durable fix when the sweep needs to add more evaluators.
